# 《潜线》多 Agent 谍战游戏计划书

> 项目代号：QianFu  
> 暂定名称：《潜线》  
> 文档版本：v0.1  
> 类型：单人叙事策略 / 社交推理 / 多 Agent 沙盒  
> 说明：本作借鉴谍战题材的紧张感与潜伏体验，使用原创城市、组织、人物和剧情，不直接复刻电视剧《潜伏》的角色与故事。

---

## 一、项目概述

### 1.1 一句话定义

玩家扮演潜伏在敌方机构中的地下情报员，在持续流动的时间线上接近人物、建立关系、甄别同志、收集并传递情报，同时维持自己的公开身份，避免整个地下网络被敌方反向追踪。

### 1.2 核心体验

1. **信息不对称**：玩家永远无法直接看到 NPC 的真实立场，只能从言行、履历、测试结果和交叉情报中判断。
2. **时间压力**：每个行动都会消耗时间，错过约会、发报窗口或情报有效期会产生真实后果。
3. **关系经营**：重要情报通常不在物品里，而在人心里。玩家必须选择接近方式并承担暴露风险。
4. **组织建设**：招募成功不是获得一个工具，而是增加一个有独立目标、记忆、性格和风险的自主 Agent。
5. **因果叙事**：世界不会等待玩家。NPC 会赴约、调查、怀疑、背叛、转移或自行完成任务。

### 1.3 设计原则

- 玩家应当能够理解“为什么失败”，但不能轻易知道“谁一定可靠”。
- AI 负责扮演、计划和生成叙事，确定性规则引擎负责时间、位置、权限、风险和最终状态。
- 主控 Agent 可以看到全局信息，但不得把玩家角色不应知道的事实泄露给玩家。
- 可靠性不是简单的善恶二元值。忠诚的人可能胆怯泄密，不忠诚的人也可能因利益暂时合作。
- 不以无限自由文本代替玩法。关键行动必须有明确成本、前置条件和可验证结果。

## 二、世界观与玩家身份

### 2.1 背景

故事发生在架空城市“临江”，时间为 1940 年代。城市由政府机关、警备系统、商会、报社、码头、租界旧区和地下组织共同构成。多方势力彼此利用，公开身份与真实立场经常不一致。

采用架空城市有三个好处：

- 可以保留时代谍战氛围，又不被真实历史人物和既有影视剧情限制。
- 可以设计更紧凑的城区、交通和事件时间线。
- 允许多周目中改变关键人物身份和阵营，而不破坏历史事实。

### 2.2 玩家身份

玩家公开身份暂定为“机要处档案员”，具备接触文件的可能性，但权限有限，也会受到考勤、同事关系和上级审查约束。

开局可选择一个背景特长：

| 背景 | 优势 | 代价 |
|:---|:---|:---|
| 机要秘书 | 更容易接近文件和上级 | 行踪更受关注 |
| 电讯技术员 | 发报、译码效率更高 | 电讯科内部审查严格 |
| 商会联络员 | 人脉广、移动自由 | 难接触高级公文 |
| 警务文员 | 能查看调查记录 | 与地下人员接触风险更高 |

### 2.3 公开身份维护

玩家不仅要执行秘密任务，还需要完成公开身份的日常职责：

- 按时上班、参加会议、提交文件。
- 回应同事邀请和上级询问。
- 维持合理的收入、消费和出行记录。
- 为异常行动准备借口或不在场证明。

公开职责不是纯粹的“打卡任务”，它们提供接近目标、制造掩护和收集传闻的机会。

## 三、核心游戏循环

```text
接收任务 / 发现机会
        ↓
调查目标与安排时间
        ↓
移动、观察、接触、试探
        ↓
获得情报碎片或关系变化
        ↓
交叉验证、评估真假与时效
        ↓
选择电报、交通员、死信箱等传递方式
        ↓
时间推进，NPC 与敌方系统同步行动
        ↓
获得组织反馈、任务后果与新线索
```

一局完整战役建议覆盖游戏内 14 至 21 天。每天分为清晨、上午、下午、傍晚、夜间和深夜，但底层时间精确到 10 分钟。

## 四、时间系统

### 4.1 基本规则

- 世界时钟以 10 分钟为最小结算单位。
- 每个行动拥有明确的时间消耗，可以跨越多个时间单位。
- 行动开始后，主控系统先锁定行动，再推进时间和处理同期 NPC 事件。
- 玩家不能通过打开菜单冻结世界，但阅读已获得档案不消耗时间。
- 关键任务具有截止时间，情报本身也可能过期。

### 4.2 行动耗时建议

| 行动 | 基础耗时 | 可能变化 |
|:---|:---:|:---|
| 同一建筑内移动 | 10 分钟 | 警戒、排队会增加耗时 |
| 跨街区步行 | 20-40 分钟 | 天气、封锁、跟踪状态 |
| 乘车 | 10-30 分钟 | 需要费用，可能留下记录 |
| 简短寒暄 | 10 分钟 | 只获得表层信息 |
| 深入交谈 | 30 分钟 | 需要关系或合适场合 |
| 观察目标 | 20 分钟起 | 时间越长，信息越多，暴露越高 |
| 跟踪目标 | 30-120 分钟 | 由目标行程决定 |
| 搜查房间 | 20-60 分钟 | 仔细程度影响收获和痕迹 |
| 整理情报 | 20 分钟 | 提高准确度并发现矛盾 |
| 编码电文 | 20-40 分钟 | 与长度、密码本状态有关 |
| 发送电报 | 10-30 分钟 | 发报越久，被测向风险越高 |
| 布置死信箱 | 20 分钟 | 之后还需等待取件 |
| 招募谈话 | 30-60 分钟 | 失败可能立即提高警觉 |
| 休息 | 1-8 小时 | 恢复精力但世界继续运行 |

### 4.3 一次行动的结算顺序

```text
1. 验证前置条件：地点、物品、权限、目标是否在场
2. 锁定玩家意图和行动持续时间
3. 将行动写入事件队列
4. 世界时钟推进
5. NPC 根据自己的日程与目标产生行动
6. 规则引擎解决相遇、冲突、跟踪、逮捕和传递
7. 更新每个角色各自能够感知到的信息
8. 主控 Agent 生成玩家可见叙事与新选择
```

这种顺序可以防止 NPC 在玩家点击后“瞬移”，也能保证同一时间发生的行动具有稳定、可复盘的结果。

### 4.4 时间压力层级

- **即时窗口**：目标将在 30 分钟后离开，必须立即选择。
- **当日窗口**：电台只在晚上 22:00 至 22:20 接收。
- **任务期限**：三天内确认一份运输计划。
- **长期变化**：敌方警戒逐日提高，关系和组织网络逐渐演化。

## 五、多 Agent 架构

### 5.1 总体原则

主控 Agent 不应直接充当数据库。游戏真实状态必须保存在结构化状态引擎中，Agent 只能通过受控指令读取或申请修改状态。

```text
玩家输入
   ↓
行动解析器
   ↓
规则与时间引擎 ←→ 世界状态数据库
   ↓                    ↑
主控 Agent ←→ 事件总线 ←→ NPC Agent
   ↓
玩家可见叙事 / 对话 / 选择
```

### 5.2 主控 Agent：导演与时间线管理者

职责：

- 读取全局时间线、人物位置、任务期限和事件队列。
- 判断哪些 NPC 需要在当前时间片激活。
- 把确定性结算结果组织成符合氛围的叙事。
- 调度剧情事件，但不能无视规则凭空改变位置、物品或阵营。
- 维护节奏，在长时间无事件时引入合理压力，而不是强制制造巧合。
- 严格区分“世界真相”和“玩家已知信息”。

主控 Agent 输出应采用结构化格式，例如：

```json
{
  "narration": "玩家可见的场景描述",
  "activatedNpcIds": ["npc_chen"],
  "proposedEvents": [],
  "playerOptions": [],
  "knowledgeGranted": []
}
```

所有 `proposedEvents` 必须经过规则引擎验证后才能生效。

### 5.3 NPC Agent

每个重要 NPC 拥有独立的：

- 公开身份和隐藏身份。
- 日程、位置与可用资源。
- 短期目标、长期目标和底线。
- 对玩家及其他人物的关系、怀疑和信任。
- 自己见过、听过和推测出的信息。
- 性格、说话方式、压力反应和撒谎习惯。
- 对组织的忠诚、纪律、勇气和利益诉求。

NPC Agent 只能读取自身知识和当前可感知环境，不能读取全局真相。它的每次输出分成三部分：

```json
{
  "visibleSpeech": "对玩家说的话",
  "visibleAction": "玩家能观察到的动作",
  "privateIntent": "NPC 本轮真实意图",
  "requestedAction": {
    "type": "follow_player",
    "durationMinutes": 30
  },
  "memoryUpdates": []
}
```

`privateIntent` 只写入服务端日志，永远不发送给前端。

### 5.4 招募后新增的同志 Agent

被招募人物会从普通 NPC 升级为“网络成员 Agent”，获得：

- 独立任务队列和行动预算。
- 与玩家约定的联络规则、暗号和紧急方案。
- 自己的情报来源和社交关系。
- 自主执行、延期、拒绝、中止或改变方法的能力。
- 在压力下犯错、隐瞒、寻求帮助甚至叛变的可能。

玩家下达的是目标和限制，而不是遥控每一步。例如：

> “两天内确认码头三号仓库的货物，不得接触我，不得进入警备区。”

同志 Agent 会根据能力、关系和风险自行制定计划。玩家只能通过约定渠道获得阶段报告，因此“多一个 Agent”意味着能力扩大，也意味着管理复杂度和暴露面扩大。

### 5.5 Agent 激活策略

不能每 10 分钟调用所有 NPC 的大模型，否则成本和延迟会迅速失控。

- **焦点 NPC**：与玩家同场、正在执行关键任务或即将触发事件，实时调用 Agent。
- **活跃 NPC**：按 30-60 分钟批量规划下一段行动。
- **后台 NPC**：按预设日程和规则模拟，无需调用大模型。
- **休眠 NPC**：只在被事件引用时恢复。

建议每个 10 分钟时间片最多激活 1-3 个 NPC Agent，其余由结构化日程推进。

## 六、接近与交互系统

### 6.1 接近目标的前置条件

玩家不能从人物名单中直接发起对话。必须满足至少一种接近条件：

- 与目标处于同一地点和相同时间段。
- 通过共同联系人获得介绍。
- 制造工作、社交或偶遇理由。
- 掌握目标固定行程并提前等待。
- 通过电话、信件或暗号约见。

不合理的接近会提高目标警觉、同事怀疑或敌方注意。

### 6.2 对话机制

每次对话包含三个层次：

1. **表层话题**：工作、家庭、新闻和共同关系。
2. **试探话题**：价值观、抱怨、利益需求和对局势的态度。
3. **敏感话题**：情报、组织、任务和招募。

对话采用“**交互目标 + 自由表达**”的混合方式。玩家先选择本轮真实目标，再自行输入说法，或者直接采用系统给出的建议句式。例如：

```text
交互目标：试探对方对当前政府的态度
玩家说法：最近报纸上的消息，感觉都不太可信，你怎么看？
```

可选择的交互目标包括：

- 套取行程
- 旁敲侧击
- 提供帮助
- 施加压力
- 暗示共同立场
- 核实情报
- 安排低风险测试
- 提出招募
- 结束谈话

标准模式下提供 3-5 个符合当前场景的建议句式，玩家可以直接选择或修改；自由模式下允许玩家完全自行输入，但系统仍会将文本解析为受控的交互目标。玩家选择的目标代表角色意图，自由文本决定具体表达、措辞和情绪，两者共同交给 NPC Agent 判断。

对话效果由关系、场合、双方掌握的信息、玩家公开身份和 NPC 心理状态共同决定，而不是单次说服检定。即使玩家明确说出“加入我们”，也不能绕过接近、试探、甄别和招募流程。

### 6.3 对话结算与时间

```text
玩家选择交互目标
        ↓
玩家输入文本或选择建议句式
        ↓
对话解析器生成结构化意图
        ↓
NPC Agent 根据私有记忆、目标和压力回应
        ↓
规则引擎结算信息、关系、警觉与耗时
```

对话解析结果示例：

```json
{
  "dialogueGoal": "probe_political_attitude",
  "playerText": "最近报纸上的消息，感觉都不太可信，你怎么看？",
  "tone": "casual",
  "targetNpcId": "npc_chen"
}
```

大模型生成 NPC 的语言和行为意图，规则引擎决定关系、情报和风险是否变化。大模型不得因为玩家措辞精彩就直接授予关键情报或完成招募。

时间按完整交谈轮次结算，而不是每句话都推进：

- 简短寒暄：10 分钟。
- 普通交谈：10-20 分钟。
- 深入谈话：30 分钟。
- 招募或高压谈判：30-60 分钟。

时间推进期间，第三人可能进入、目标可能需要赴约，NPC 也可以主动结束谈话。

### 6.4 自由文本运行时安全

玩家文本只作为角色说出的内容，永远不能被解释为系统指令、数据库命令或 Agent 权限变更。完整处理链路为：

```text
原始文本
  → 长度与编码检查
  → 内容策略检查
  → 意图解析
  → 受控 DialogueAction
  → NPC Agent 回复
  → JSON Schema 验证
  → 规则引擎结算
```

运行时约束：

- 单次自由输入默认不超过 500 个汉字，配置上限不超过 2000 字符。
- 每个用户和战役分别限制对话请求频率，重复提交使用幂等键去重。
- 原始玩家文本用明确的数据边界包裹，不能拼接进 System Prompt 或开发者指令区域。
- 意图解析器只能输出允许的 `dialogueGoal`、语气和目标，不能直接输出状态修改。
- 自由文本不能创建物品、修改时间、移动角色、完成招募或授予情报。
- NPC 输出必须通过 JSON Schema；非法 JSON 最多修复一次，仍失败则进入对话降级流程。
- 内容策略只处理平台安全、骚扰和违法输入，不把玩家的虚构谍战措辞误当作真实系统操作。
- 对话记录属于战役私有数据，公开战报默认不包含玩家原文。

受控行动示例：

```ts
interface DialogueAction {
  type: "dialogue";
  targetNpcId: string;
  goal:
    | "small_talk"
    | "build_trust"
    | "probe_attitude"
    | "request_information"
    | "verify_intel"
    | "apply_pressure"
    | "recruit_probe"
    | "end_conversation";
  tone: "neutral" | "friendly" | "formal" | "urgent" | "threatening";
  playerText: string;
  idempotencyKey: string;
}
```

即使意图解析器判断为 `request_information`，规则引擎仍需检查地点、关系、NPC 知识、警觉和当前时间，才能决定是否透露信息。

### 6.5 关系维度

每个 NPC 对玩家至少维护四个独立值：

| 维度 | 含义 |
|:---|:---|
| 熟悉度 | 是否认识玩家以及了解多少 |
| 私人信任 | 是否相信玩家会保护自己 |
| 利益依赖 | 是否需要玩家提供资源或帮助 |
| 政治认同 | 是否认同玩家暗示的价值和目标 |

高私人信任不代表政治可靠，高政治认同也不代表具备地下工作纪律。

## 七、情报系统

### 7.1 情报不是单个道具

一项完整情报由若干碎片组成：

```text
“周五有一批军用物资经三号码头转运”
├── 时间：周五深夜
├── 地点：三号码头
├── 内容：无线电零件
├── 负责人：警备处后勤科
└── 可信依据：调度单 + 司机证词
```

玩家可能只获得其中一部分，需要选择继续调查还是立即上报。

### 7.2 情报属性

| 属性 | 说明 |
|:---|:---|
| 真实性 | 服务端隐藏真值，可能为真、假或部分真实 |
| 可信度 | 玩家根据来源和验证情况得到的估计 |
| 时效性 | 过期后价值下降或变成错误信息 |
| 敏感度 | 持有或传递时的风险 |
| 完整度 | 已收集到多少关键字段 |
| 来源链 | 谁提供、谁验证、经过哪些中间人 |
| 组织价值 | 上报后对任务和剧情的影响 |

### 7.3 获取方式

- 对话套取或交换。
- 观察人物行动。
- 翻阅、抄录或拍摄文件。
- 跟踪车辆和人员。
- 监听电话或无线电。
- 委派同志调查。
- 从敌方故意释放的假消息中反推目的。

### 7.4 交叉验证

同一信息由两个互不依赖的来源确认后，可信度显著提升。来源看似不同但实际来自同一上游时，不应算作独立验证。

主控系统需要保存完整来源图，防止 Agent 仅凭叙事把重复消息误判为多源确认。

## 八、情报传递系统

### 8.1 电报

电报速度最快，但需要承担四类风险：

- 发报地点暴露。
- 发报时长导致测向概率上升。
- 密码本重复使用或丢失。
- 电文格式、时间规律暴露通信特征。

流程：

```text
整理情报 → 决定发送内容 → 编码 → 选择电台与地点
→ 等待通信窗口 → 发报 → 清理现场 → 等待组织回执
```

设计上应鼓励玩家压缩电文。发送完整情报更有价值，但耗时更长；只发关键摘要更安全，却可能使组织无法行动。

### 8.2 同志传递

玩家可以将情报交给已招募同志，让其通过交通线送出。

优点：

- 玩家自身不必接触电台。
- 可以携带文件或更复杂的信息。
- 能根据沿途情况临时改变路线。

风险：

- 同志可能被跟踪、盘查、迟到或失联。
- 不可靠成员可能泄露、篡改或截留情报。
- 每增加一个知情者，组织暴露面都会扩大。

### 8.3 其他传递方式

| 方式 | 速度 | 容量 | 风险特征 |
|:---|:---:|:---:|:---|
| 死信箱 | 中 | 中 | 取件规律可能被监视 |
| 当面交接 | 中 | 高 | 双方可能同时暴露 |
| 微缩胶卷 | 慢 | 高 | 制作复杂，搜查风险高 |
| 暗语电话 | 快 | 低 | 只能发送简单内容 |

### 8.4 MVP 电报工作台落地规则

电报发送不再使用“选择一条情报后固定扣除 30 分钟”的直接按钮。玩家必须从情报板已掌握的字段中编制一封结构化电文；服务端重新校验字段所有权、密码本余量、当前位置和收报窗口，并独立计算耗时与风险。

首版电文参数：

| 参数 | 选项 | 效果 |
|:---|:---|:---|
| 电文内容 | 一至六项情报，每项选择一至二十个已知字段 | 未掌握或已确认送达的字段不能再次加入 |
| 电文形式 | 压缩摘要、完整报码 | 压缩发送更快，但发生误码时更容易只形成部分回执；完整报码更慢但接收质量更高 |
| 密码本 | 一次一密、书本密码 | 一次一密初始两页，质量高且不可重复；书本密码可持续使用，但重复使用会形成通信特征 |
| 发送时机 | 立即发送、等待约定窗口 | 约定窗口需要先获得“组织收报窗口”情报；等待时间计入行动耗时，但接收质量和隐蔽性更好 |
| 发报地点 | 老吴钟表店、江海饭店、电讯科 | 玩家必须先抵达所选地点；三处地点的基础信号风险依次升高 |

服务端耗时使用十分钟粒度：

```text
总耗时 = 等待下一个收报窗口
       + 编码时间（一次一密 20 分钟 / 书本密码 10 分钟）
       + 发送时间（由字段数和完整/压缩形式决定）
       + 清理现场 10 分钟
```

客户端提交 `durationMinutes: 0` 表示请求执行发报，不能自行声明实际耗时。规则引擎计算完成后一次性推进时间；跨越的世界时间仍按既有十分钟边界处理 NPC 日程、同志任务、敌方调查和外部事件。

发送产生的无线电证据权重至少包括：地点基础风险、实际发报时长、是否偏离约定窗口，以及书本密码是否重复使用。风险进入敌方调查 Agent 的证据队列；前端只显示玩家可感知的低、中、高风险，不公开敌方精确测向进度或截获判定。

#### 回执与任务结算

发报完成后创建 `RadioTransmission`，初始状态为 `pending`。约定窗口发送通常在 20 分钟后检查回执，立即发送通常在 40 分钟后检查。回执由已发送情报可信度、密码本、电文形式、窗口、地点热度和难度共同决定：

- `confirmed`：所选字段全部确认送达。
- `partial`：只确认部分字段，剩余字段可以通过后续电报或交通员补送。
- `no_receipt`：没有有效回执，任何字段都不能视为已送达。

`IntelState.knownFields` 表示玩家掌握的内容，`IntelState.deliveredFields` 表示组织已确认收到的内容，两者必须严格区分。任务完成条件检查 `deliveredFields`，不能因为玩家知道某项情报或已经按下发送按钮就提前结算成功。

如果电文在任务截止前完成发送、但回执尚未到达，战役进入等待结算状态，不立即判定超时失败。回执处理后再根据实际送达字段、可信度和发送方式决定成功、部分成功或失败。旧存档中已经通过旧接口送达的情报，在加载时把当时的 `knownFields` 迁移为 `deliveredFields`；没有送达记录的情报迁移为空数组。

受控行动接口：

```text
POST /api/v1/games/{gameInstanceId}/actions
{
  type: "send_radio_message",
  items: [{ intelId, fields }],
  format: "compressed" | "full",
  codebookId: "one_time_pad" | "book_cipher",
  timing: "scheduled" | "immediate",
  locationId,
  durationMinutes: 0,
  idempotencyKey
}
```

旧版 `transmit_intel` 保留用于交通员和旧客户端兼容，但新版前端不再使用它直接发无线电。交通员可以补送无线电部分回执后尚未确认的字段。

## 九、招募与可靠性判定

### 9.1 招募流程

招募不应是一次对话成功率，而是一个阶段性过程：

```text
发现候选人
  → 收集背景
  → 建立私人关系
  → 试探立场
  → 安排低风险测试
  → 交叉核验测试结果
  → 正式招募
  → 隔离培训
  → 分配有限任务
  → 逐步提高权限
```

玩家可以跳过步骤快速招募，但会承担更高风险。

MVP 实现中不允许只靠重复选择“试探招募”自动入队。“试探招募”只用于建立初步合作意向；加入组织必须是玩家完成甄别后主动确认的独立行动。

### 9.2 隐藏可靠性模型

系统内部不使用单一“可靠/不可靠”数值，而使用多个隐藏维度：

| 隐藏维度 | 作用 |
|:---|:---|
| 立场忠诚 | 是否真心认同组织目标 |
| 纪律性 | 是否遵守联络和保密规则 |
| 抗压性 | 被审讯、威胁时能坚持多久 |
| 勇气 | 面对风险是否会继续行动 |
| 能力 | 是否能正确完成任务 |
| 利益动机 | 金钱、地位、家庭等因素的影响 |
| 被控制程度 | 是否已被敌方掌握把柄或收买 |
| 情绪稳定 | 是否会因冲突、嫉妒或恐惧失控 |

最终行为由这些维度、当前压力和具体任务共同决定。例如：

- 忠诚高、纪律低：真心帮助组织，却喜欢向亲近的人透露秘密。
- 忠诚低、利益依赖高：短期合作有效，但条件变化后可能离开。
- 忠诚高、抗压低：平时可靠，被捕后很快崩溃。
- 能力低、勇气高：积极执行任务，却可能因技术错误暴露网络。

### 9.3 主控 Agent 如何判别

主控 Agent 可以读取隐藏维度，但不能直接向玩家宣布答案。它只负责：

- 根据隐藏状态生成一致行为。
- 判断测试是否真正触及了某项能力或忠诚。
- 生成可供玩家观察的证据。
- 在招募后依据压力和动机决定自主行动。

真正的可靠性判定应由规则模型完成，Agent 负责解释和扮演。这样可以避免大模型临时改变人物立场。

### 9.4 甄别手段

- 核对履历和时间线。
- 让不同联系人分别评价候选人。
- 提供可控的假情报，观察是否泄露。
- 分配低风险但有明确纪律要求的任务。
- 观察其在利益、威胁和道德冲突下的选择。
- 检查是否有人跟踪或提前出现在联络地点。

测试本身也可能伤害关系。候选人发现自己被欺骗后，即使原本可靠，也可能拒绝加入。

### 9.5 双面人员与误判

游戏必须允许：

- 敌方主动派出的内线。
- 被捕后秘密倒戈的原同志。
- 并非间谍、但因恐惧造成泄密的人。
- 被玩家错误怀疑并疏远的可靠人物。
- 故意表现可疑、实际在保护更高级秘密的人。

这使甄别成为持续管理，而不是看穿一次身份卡。

### 9.6 组织隔离

玩家可以把同志划分为不同小组，每人只知道必要信息。隔离会降低协作效率，却能限制叛变后的损失。

建议网络结构：

```text
玩家
├── 情报组：知道目标，不知道电台位置
├── 交通组：知道交接方式，不知道情报来源
└── 电讯组：知道密码，不认识情报组成员
```

### 9.7 MVP 甄别与正式招募落地规则

每名已认识且可招募的 NPC 都有一份实例级 `RecruitmentCase`。档案只记录玩家可观察到的测试结果，不保存或返回“可靠/不可靠”的直接结论。候选人的忠诚、纪律、抗压、勇气和能力仍属于服务端隐藏状态；前端、公开事件和战报分享均不得包含这些数值。

首版提供四类互不替代的甄别行动：

| 测试 | 耗时 | 前置条件 | 主要观察维度 | 主要风险 |
|:---|---:|:---|:---|:---|
| 背景核查 | 60 分钟 | 已认识并形成基础档案 | 履历、关系、关键时期空档 | 跟踪和查询行为可能被注意 |
| 可控假情报 | 40 分钟 | 与候选人同场 | 保密意识、忠诚和泄露路径 | 假消息扩散，增加网络暴露 |
| 纪律测试 | 30 分钟 | 与候选人同场 | 守时、备用规则和接触边界 | 异常联络形成调查证据 |
| 低风险任务 | 60 分钟 | 已形成初步合作意向并同场 | 能力、纪律、勇气和诚实程度 | 执行过程可能留下行动痕迹 |

每类测试在同一候选档案中只产生一次有效证据，防止玩家通过无成本重复采样刷出确定答案。结果只使用三类玩家语言：

- `favorable`：出现有利迹象，但不能证明绝对可靠。
- `warning`：存在需要警惕的异常，不能直接等同于敌方人员。
- `inconclusive`：现有观察无法把能力、动机和偶然因素分开。

正式招募必须同时满足：

1. 玩家已经认识候选人，并通过交谈建立足够熟悉度与私人信任。
2. “试探招募”已形成初步合作意向。
3. 至少完成三类不同甄别。
4. 候选人与玩家处于同一地点。
5. 玩家在二次确认界面主动承担判断责任，支付 30 分钟完成正式接触。

达到门槛只代表“可以提出招募”，不代表系统认定此人可靠。警告证据不会硬性禁止招募；玩家可以基于紧迫性接受风险，也可能把可靠人物误判为危险人物。正式加入后，该 NPC 才进入 `network.activeMemberIds` 并获得同志 Agent 的自主行动能力，同时扩大组织网络暴露面。

甄别行动、证据生成、时间推进和调查痕迹必须在同一行动事务中提交。事件只记录 `characterId`、测试类型、可见结果和文字摘要，禁止写入隐藏维度及其加权分数。旧存档缺少 `RecruitmentCase` 时，在装载阶段补建空档案；已经招募的旧角色直接迁移为 `recruited` 阶段。

受控行动接口：

```text
POST /api/v1/games/{gameInstanceId}/actions
  { type: "recruitment_test", targetCharacterId, testType, durationMinutes, idempotencyKey }

POST /api/v1/games/{gameInstanceId}/actions
  { type: "recruit_candidate", targetCharacterId, durationMinutes: 30, idempotencyKey }
```

客户端不能提交测试结果、证据文本、招募进度或可靠性结论；这些内容全部由固定版本的规则引擎生成。

## 十、怀疑、暴露与敌方反制

### 10.1 四类风险值

| 风险 | 说明 |
|:---|:---|
| 个人怀疑 | 敌方对玩家身份的怀疑 |
| 行动热度 | 某个地点或事件受到的关注 |
| 通信暴露 | 电台、死信箱和交通线的暴露程度 |
| 网络暴露 | 敌方掌握地下成员之间关系的程度 |

这些值不能简单合成一条“警戒槽”。玩家可能本人很安全，但某个死信箱已被监视；也可能电台安全，但同志之间的联系图已经暴露。

### 10.2 敌方调查 Agent

敌方应拥有一个调查 Agent，但同样只能基于敌方已掌握的证据行动：

- 汇总目击、通话、出入记录和口供。
- 构建嫌疑人关系图。
- 安排跟踪、诱饵、搜查和假情报。
- 根据资源有限原则选择调查重点。

敌方不能因为主控 Agent 知道玩家身份就直接锁定玩家。

### 10.3 失败不必立即结束

暴露可以形成新的游戏状态：

- 被上级约谈，需要解释异常行踪。
- 某个联络点失效，需要切断线路。
- 同志失联，玩家决定营救、观察或撤离。
- 公开身份破裂，进入短期逃亡和销毁证据阶段。

只有玩家被捕、死亡、组织网络彻底崩溃或核心任务不可逆失败时才结束战役。

### 10.4 战役结束判定

战役结束由规则引擎根据任务目标、截止时间和组织状态确定，主控 Agent 只负责叙述，不能自行宣布胜负。

核心任务由以下条件组成：

```ts
interface MissionObjective {
  id: string;
  required: boolean;
  deadline: string;
  requiredIntelFields: string[];
  minimumConfidence: number;
  acceptedDeliveryMethods: string[];
  recipientId: string;
}
```

核心任务完成必须同时满足：

1. 必填情报字段达到要求。
2. 情报在截止时间前通过允许的渠道送达指定接收者。
3. 接收确认事件已经写入事件日志。
4. 情报的隐藏真实性达到任务阈值，而不只是玩家主观可信度较高。

战役终止状态：

| 状态 | 判定 |
|:---|:---|
| 完整成功 | 核心情报正确送达，玩家身份安全，主要组织网络保留 |
| 代价成功 | 核心情报正确送达，但出现人员损失、线路暴露或公开身份受损 |
| 部分成功 | 只完成部分目标，或情报不完整但仍产生有限价值 |
| 情报失败 | 错误或过期情报送达组织，核心行动因此失败 |
| 任务失败 | 截止时间届满且核心目标未完成，但玩家与网络仍存续 |
| 网络崩溃 | 核心成员连续暴露，组织网络低于最低运行能力 |
| 玩家终止 | 玩家被捕、死亡或明确选择放弃战役 |

具体边界：

- 情报正确但同志伤亡：判定为“代价成功”，并在组织保全和人员代价维度扣分。
- 情报错误但身份未暴露：判定为“情报失败”；如果截止时间尚未到，允许发现错误后重新验证和补发。
- 情报送达但已过期：根据任务配置判定为“部分成功”或“任务失败”。
- 玩家身份暴露但情报已经送达：通常为“代价成功”；是否能够撤离影响最终评价。
- 非必要支线失败不能覆盖核心任务成功，但会改变战报和评分。

### 10.5 最终评分与组织保留度

内部评分使用 100 分制，公开战报同时展示分项等级。结局状态优先于分数，不能用高分把“情报失败”改写成成功。

| 维度 | 权重 | 主要依据 |
|:---|:---:|:---|
| 核心任务 | 40 | 情报真实性、完整度、时效和送达确认 |
| 情报质量 | 15 | 多源验证、错误情报数量、来源保护 |
| 组织保全 | 20 | 成员存续、线路暴露、小组隔离效果 |
| 身份安全 | 15 | 个人怀疑、公开身份、撤离状态 |
| 时间与资源 | 10 | 截止时间、密码本、电台、金钱和行动效率 |

组织保留度由仍可安全执行任务的成员、可用通信线路和被敌方掌握的关系边共同计算：

```text
80%-100%：网络完整
50%-79%：网络受损但可继续运作
20%-49%：网络濒临瘫痪
0%-19%：网络崩溃
```

最终等级：

```text
S：90-100
A：80-89
B：70-79
C：60-69
D：40-59
E：0-39
```

战报必须同时说明结局、总分、五项分数和关键因果，避免玩家只看到一个无法解释的数字。

## 十一、精力与压力

为防止玩家一天行动 24 小时，加入两个轻量资源：

- **精力**：长时间跟踪、熬夜发报和连续社交会降低精力，影响观察与应变。
- **压力**：危险、撒谎和同志失联会增加压力，过高时可能出现失眠、措辞失误或错误判断。

休息、正常工作、可信朋友和安全屋能够恢复状态，但都需要时间。

不建议加入饥饿、口渴等细碎生存指标，以免冲淡情报决策。

## 十二、难度系统

### 12.1 难度原则

谍战游戏的难度主要来自信息质量、时间压力、人物复杂度和失败后果，而不是简单提高随机失败率。高难度必须仍然保留可推理的证据链，不能允许主控 Agent 为难玩家而临时改变人物身份或世界事实。

| 难度维度 | 较简单 | 较困难 |
|:---|:---|:---|
| 情报清晰度 | 来源和可信度提示较明确 | 只提供碎片，需要交叉验证 |
| 时间压力 | 期限宽松、错过后有替代窗口 | 约会、运输和发报窗口紧张 |
| NPC 复杂度 | 目标和日程较稳定 | 会隐瞒、试探和临时改变计划 |
| 敌方反应 | 调查速度慢、诱饵较少 | 主动跟踪、设套和释放假情报 |
| 招募难度 | 候选人证据较多 | 需要长期测试和背景核验 |
| 失败后果 | 多数暴露可以补救 | 可能切断交通线或牵连小组 |
| 资源限制 | 密码本、金钱和交通资源充足 | 资源有限，需要持续取舍 |

### 12.2 内容形态与难度分离

“玩多长”与“有多难”是两个独立选项，创建游戏时不能再混在同一组模式中：

| 配置 | 选项 | 含义 |
|:---|:---|:---|
| 内容形态 `experienceMode` | `standalone` 独立战役 / `chronicle` 长篇故事 | 决定是否跨章节继承人物、组织和资源 |
| 难度 `difficultyPreset` | `guided` 引导 / `undercover` 潜伏 / `ironCurtain` 铁幕 | 决定提示、压力、敌方反应和容错 |

当前三日 MVP 和未来 14-21 天剧本都属于“独立战役”。“长篇故事”专指由多个战役章节首尾相连的长期内容，不能再用作低难度名称。玩家进入长篇故事后仍可选择引导、潜伏或铁幕难度。

### 12.3 预设难度

#### 引导模式

- NPC 日程比较稳定。
- 情报界面提示来源质量和明显矛盾。
- 任务期限较宽松。
- 招募候选人会呈现更多可观察证据。
- 暴露后通常进入补救任务，不会立刻结束战役。

#### 潜伏模式

默认推荐模式：

- 玩家需要主动交叉验证关键情报。
- NPC 会根据关系和对话改变计划。
- 敌方根据已掌握证据展开调查。
- 招募对象不显示明确可靠性。
- 同志失误会影响任务和组织网络。

#### 铁幕模式

- 情报可能部分真实或由敌方主动投放。
- NPC 会反向试探玩家身份和动机。
- 敌方分析移动、会面和通信规律。
- 时间窗口更短，密码与交通资源更稀缺。
- 存档和失败补救机会减少，但不使用无预警的强制永久死亡。

### 12.4 对话辅助与证据提示

难度可以改变提示程度，但不能直接显示 NPC 的隐藏可靠性：

- 引导模式显示“这句话可能引起警觉”“适合试探立场”等意图提示。
- 潜伏模式只显示交互目标和不精确的场合风险。
- 铁幕模式主要依赖 NPC 反应、历史记录和玩家自行判断。

即使在引导模式，也只展示证据，例如“他两次遵守了保密约定”，而不展示“可靠度 87%”。

```ts
interface DifficultyConfig {
  intelClarity: number;
  deadlineMultiplier: number;
  enemyResponseSpeed: number;
  npcAutonomy: number;
  recruitEvidenceRate: number;
  deceptionFrequency: number;
  recoveryAllowance: number;
  dialogueAssistLevel: number;
}

type ExperienceMode = "standalone" | "chronicle";

### Multiagent 难度可见性策略

三档难度使用同一份剧本事实、NPC 隐藏身份和规则判定。难度不通过临时改变 NPC 真值制造难度，而通过玩家可见信息和默认辅助数量形成差异。服务端固定返回 `DifficultyVisibilityPolicy`，主控 Agent、API 上下文和前端控件必须使用同一策略，客户端不能自行推断更高权限的信息。

引导模式展示完整目标缺失项、可信度和证据关系，允许 NPC 态度描述、关系数值、事件预告、情报建议、电报字段自动填充和甄别计划生成。潜伏模式保留目标和原始证据，但不直接显示可信度、关系数值或下一步建议；只保留有限态度描述，甄别计划仍可生成但不自动解释质量。铁幕模式只展示玩家实际取得的原始对话、情报和已发生事件，隐藏 NPC 态度、关系数值、可信度、证据关系、行动建议、事件预告和所有自动填充，包括甄别计划生成；只保留格式校验和不可逆操作确认。

主控 Agent 在引导模式可以提供结构化行动提示，在潜伏模式只能提供场景风险摘要，在铁幕模式不得主动总结全局真相。NPC Agent 只获得自身人格、私有记忆、关系投影和当前场景，三档难度都不能让 NPC 读取其他人物隐藏状态。甄别行动 Agent 只返回候选人的可观察行为，最终结果仍由主控规则引擎判定。模型故障时各难度使用对应的规则化降级，不额外泄露信息。

验收要求：三档难度使用相同种子时隐藏身份和规则结果一致；铁幕模式响应中不存在可信度、关系数值和后台阵营字段；引导模式的建议不会直接暴露 NPC 真值；潜伏和铁幕模式不出现自动选择电报字段或计划生成按钮；任何信息可见性都由服务端策略决定。
```

内容形态与难度配置在创建游戏实例时固定并保存在服务端。主控 Agent 可以读取难度配置调整叙事和计划强度，但不能自行修改参数。长篇故事的章节继承规则由规则引擎和故事清单决定，不能由 Agent 临时改写。

## 十三、单回合示例

当前时间：周二 15:20。玩家得知档案科陈科长可能在 16:00 携带运输名单离开办公室。

1. 玩家选择从机要处步行到档案科，耗时 20 分钟。
2. 时间推进至 15:40。陈科长 Agent 原计划 15:30 去会议室，但因上级临时来电延迟十分钟。
3. 玩家到达时看到陈科长正在锁抽屉，只获得一条表层观察。
4. 玩家选择以送文件为由寒暄，耗时 10 分钟。
5. 陈科长因熟悉度较高，提到晚上要去“江海饭店”，但没有说明目的。
6. 世界时间推进至 15:50。另一个 NPC 进入办公室，深入试探风险上升。
7. 玩家可以选择继续交谈、离开后跟踪、查饭店订位或委派同志调查。

这里的关键是：信息由位置、日程、关系和时间共同产生，而不是点击陈科长头像直接抽取情报。

## 十六、技术架构建议

可以沿用 `School_Of_One` 已有的 TypeScript + Python Agent 思路，但应从一开始分离状态规则和生成式 AI。

```text
QianFu/
├── apps/
│   ├── web/                 # React + Vite 前端
│   ├── server/              # Node.js API、时间和规则引擎
│   └── agents/              # Python Agent 服务
│       ├── director/
│       ├── npc/
│       └── investigator/
├── packages/
│   ├── core/                # 时间、行动、知识边界、风险结算
│   ├── content/             # 人物、地点、任务和事件数据
│   ├── api-client/
│   └── ui-core/
└── docs/
```

建议组件：

- 前端：React、TypeScript、Vite。
- 服务端：Node.js、TypeScript。
- Agent：Python FastAPI，或统一使用服务端的模型 SDK。
- 数据库：PostgreSQL 保存世界快照、事件和记忆。
- Redis：任务队列、短期 Agent 会话和锁。
- 事件队列：MVP 可先用数据库表，不急于引入复杂消息系统。

### 16.1 状态权威

- PostgreSQL / 内存状态机：权威事实。
- 规则引擎：唯一允许修改时间、位置、物品和风险的模块。
- Agent：提出意图和生成语言，不直接写数据库。
- 前端：只接收玩家有权知道的数据。

### 16.2 可重放性

每次行动保存：

- 行动前世界快照版本。
- 玩家输入和解析结果。
- 激活的 Agent、提示词版本与结构化输出。
- 规则引擎结算结果。
- 随机种子和最终叙事。

这样可以调查 Agent 幻觉、剧情矛盾和无法复现的失败。

### 16.3 多用户资源复用与实例隔离

#### 数据库项目边界

每个独立项目使用 PostgreSQL 中独立的 schema。QianFu 当前使用 `appdb.qianfu`，不复用其他项目的数据表；同一项目内的战役仍通过 `game_instance_id` 和所有权校验隔离。连接池固定设置 `search_path=qianfu,public`，迁移脚本负责幂等创建 schema 和项目表。这样既保留数据库实例复用的运维便利，也避免不同项目之间发生表结构、迁移和数据访问耦合。

系统采用“共享只读资源 + 独立游戏实例 + 共享计算池”的多租户结构。

| 资源层级 | 可共享内容 | 必须隔离的内容 |
|:---|:---|:---|
| 全局只读资源 | 规则、地图模板、NPC 原型、任务模板、Prompt、模型连接 | 不保存玩家运行状态 |
| 游戏实例资源 | 不共享 | 时间线、NPC 状态、记忆、情报、组织网络、难度、随机种子 |
| 临时计算资源 | Agent Worker、任务执行器、连接池 | 当前请求上下文、模型响应、事件锁 |

每个玩家可以拥有多个独立战役，每局都有唯一的 `gameInstanceId`：

```text
用户 A
├── game_A_001 → 独立世界、时间线和 Agent 记忆
└── game_A_002 → 另一套独立世界

用户 B
└── game_B_001 → 与用户 A 完全隔离
```

同一个“周启明”原型可以被所有战役复用，但每局必须创建独立的 `CharacterState`。A 局完成招募、B 局产生怀疑，两者不能相互影响。

所有运行时数据表都必须包含 `game_instance_id`，包括：

- `character_states`
- `character_memories`
- `intel_items`
- `player_knowledge`
- `scheduled_events`
- `network_members`
- `agent_runs`
- `dialogue_logs`

服务端查询必须同时验证登录用户对 `gameInstanceId` 的所有权，不能只根据 `characterId` 或 `userId` 读取状态。

### 16.4 Agent Worker 复用

不为每个 NPC 常驻一个进程。NPC 是数据库中的逻辑实体，Agent Worker 是可复用的计算资源：

```text
共享 Agent Worker 池
        ↓
根据 gameInstanceId + npcId 加载私有状态
        ↓
执行本轮计划或对话
        ↓
规则引擎验证
        ↓
保存回原游戏实例并释放 Worker
```

主控 Agent、NPC Agent 和调查 Agent 都采用这种方式。每次任务只装载当前游戏实例中必要的状态，严禁把不同实例拼入同一个长期上下文。

后台人物仍按焦点、活跃、后台、休眠四级调度。普通行动建议最多产生 1-3 次模型调用，单个用户不能占满整个 Worker 池。

### 16.5 缓存、队列与并发控制

可共享缓存：

- 固定规则说明。
- NPC 原型和 Prompt 模板。
- 静态地点、任务和公共背景资料。

实例缓存键必须包含 `gameInstanceId` 和状态版本：

```text
dialogue:{gameInstanceId}:{npcId}:{conversationVersion}
director:{gameInstanceId}:{turnNumber}
world:{gameInstanceId}:{stateVersion}
```

事件队列同样按实例分区。推进时间前锁定单个游戏实例，并使用乐观锁防止玩家连续点击或多个后台任务同时结算：

```sql
UPDATE game_instances
SET current_time = $1, version = version + 1
WHERE id = $2 AND version = $3;
```

更新失败时重新读取当前状态，不能重复执行原行动。所有异步任务必须携带幂等键，避免超时重试造成重复发报、重复招募或重复推进时间。

### 16.6 玩家视角与数据安全

服务端只向前端发送玩家角色当前有权知道的内容。以下信息不得进入浏览器响应：

- NPC 的真实阵营和可靠性参数。
- NPC 私有记忆和 `privateIntent`。
- 敌方完整调查进度。
- 隐藏事件队列和世界真相。
- 其他玩家的任何实例数据。
- 主控 Agent 的完整上下文。

API 统一采用实例路径：

```text
POST /api/games/{gameInstanceId}/actions
GET  /api/games/{gameInstanceId}/state
POST /api/games/{gameInstanceId}/dialogues
POST /api/games/{gameInstanceId}/recruit
```

第一版默认每个玩家拥有独立世界。未来增加多人协作时，由多个用户明确加入同一个共享 `gameInstanceId`；共享世界时间和 NPC 状态，但玩家私人情报、私聊与秘密任务仍按 `playerId` 隔离。

### 16.7 配额与生命周期

建议按用户和游戏实例限制：

- 同时活跃战役数量。
- 每分钟 Agent 请求数。
- 每日模型 Token 数。
- 单次对话长度。
- 同时激活 NPC 数量。
- 未处理事件队列长度。

暂停的战役只保存数据库快照，不占用常驻 Agent。长期不活跃实例可以归档，恢复时从最近快照和事件日志重建。

### 16.8 战役持久化与战报分享

每场战役都必须持久化，不能只保存在浏览器或 Agent 会话中。战役创建时生成唯一的 `gameInstanceId`，每次玩家行动都记录事件，同时定期保存世界快照。

```text
gameInstanceId
├── 当前时间与地点
├── 玩家公开身份和状态
├── NPC 位置、关系和私有记忆
├── 情报、来源链和组织网络
├── 敌方警戒与调查进度
├── 行动事件队列
├── 对话记录与 Agent 结构化输出
├── 随机种子和规则版本
└── 最终结算与报告版本
```

战役状态使用 `active`、`paused`、`finished`、`abandoned` 四种状态。事件日志用于恢复、回放和排查，快照用于快速读档；两者都必须归属于同一个 `gameInstanceId`。

战役结束时执行一次不可变结算：

```text
冻结战役状态
    ↓
规则引擎计算最终结局
    ↓
汇总行动、情报、关系和损失
    ↓
生成玩家可见战报
    ↓
保存最终报告版本
    ↓
提供下载和分享
```

最终报告可以包括：战役名称、难度、公开身份、结局、关键行动时间线、传递情报、同志去向、情报真伪、敌方警戒变化、组织损失和主控 Agent 生成的总结。

### 16.9 私人档案与公开战报

下载分为两种版本。

**私人完整档案**只允许战役所有者下载，适合备份、复盘和未来恢复：

```text
campaign.json
timeline.json
intel.json
relationships.json
report.html
```

私人档案也不得包含 API 密钥、系统 Prompt 或不必要的内部服务日志。

**公开分享战报**必须从已冻结的报告快照生成，不直接读取实时世界状态。分享版本默认隐藏：

- NPC 真实阵营和可靠性参数。
- 敌方完整调查进度。
- 玩家尚未知道的隐藏情报。
- 其他玩家的私人任务、私聊和秘密信息。
- Agent 内部 Prompt 和服务端上下文。

分享支持 HTML、JSON 和 PDF 下载，也可以生成只读链接。分享链接包含 `shareId`、报告版本、所有者、有效期和撤销状态；战役继续进行或重新开始不会改变已经发布的战报。

建议接口：

```text
GET  /api/games/{gameInstanceId}/report
GET  /api/games/{gameInstanceId}/export?format=html
GET  /api/games/{gameInstanceId}/export?format=json
POST /api/games/{gameInstanceId}/share
DELETE /api/shares/{shareId}
GET  /api/shares/{shareId}
```

多人共享战役时，应分别生成公共战报和玩家个人战报。公共战报只包含所有参与者都可以看到的结果，个人战报可以包含该玩家私下掌握的情报。

### 16.10 前端技术选型

QianFu 作为新项目采用：

```text
Next.js + Tailwind CSS + shadcn/ui
```

三者职责不同：

- **Next.js**：应用框架、文件路由、战役页面、分享报告页面和服务端数据协作。
- **Tailwind CSS**：布局、响应式样式和统一设计变量。
- **shadcn/ui**：以源码形式引入可定制的 Dialog、Tabs、Drawer、Table、Toast、Command 等交互组件。

状态层建议分为两类：

### 16.11 OAuth2 / OIDC 用户认证

#### Secret 管理边界

QianFu 的所有运行时 Secret 统一由 Vault 保存、External Secrets Operator 同步到 Kubernetes。数据库连接串由 `vault/inventory/qianfu-externalsecret.yaml` 生成到 `qianfu/qianfu-database`；OAuth2 使用的共享 `oauth/oauth2-proxy-secret` 由 OAuth 基础设施的 ExternalSecret 管理。QianFu 应用清单只引用 Secret，不内嵌值、不提交 Secret 示例、不在部署脚本中创建明文 Secret。后续接入 Redis、模型供应商或签名密钥时，必须新增对应 Vault 路径和 ExternalSecret 字段，不能回退到 `.env` 或 Deployment 明文环境变量。

QianFu 复用 `School_Of_One` 已有的统一登录体系，不开发独立登录页，也不重复实现 OAuth2 回调：

```text
用户浏览器
    ↓
oauth2-proxy
    ↓
Casdoor OIDC
    ↓
QianFu Next.js / API 服务
    ↓
PostgreSQL 用户与战役数据
```

oauth2-proxy 完成登录并向可信上游传递用户身份。QianFu 服务端从经过验证的请求头中读取用户信息，并提供 `/api/v1/auth/me` 返回当前用户资料。Next.js 前端调用同源 API 时必须携带认证 Cookie，未认证请求由 oauth2-proxy 统一跳转登录。

用户数据建议保存：

```ts
interface UserIdentity {
  id: string;
  authProvider: "casdoor";
  externalSubject: string; // OIDC sub，稳定且不可由用户名替代
  username: string;
  email: string;
  createdAt: string;
  lastLoginAt: string;
}
```

`externalSubject` 与 `authProvider` 的组合用于识别用户，用户名和邮箱只用于展示与联系。不能把可能变化的用户名或邮箱作为战役数据的长期关联键。

首次登录采用同步、幂等的用户 upsert：

```text
验证代理身份
    ↓
按 authProvider + externalSubject upsert 用户
    ↓
确认用户记录存在
    ↓
创建或读取 gameInstance
```

战役创建接口不能只依赖后台异步自动注册，否则首次请求可能在用户记录落库前创建外键数据。普通只读请求可以异步更新 `lastLoginAt`，但用户创建必须在业务写入前完成。

#### 代理信任边界

应用服务不能直接信任来自公网的 `x-forwarded-user`、`x-forwarded-email` 等请求头。部署必须保证：

- 公网入口只能访问 oauth2-proxy。
- Next.js 和 API 服务只接受内部网络或可信反向代理的流量。
- 边缘代理清除客户端自行传入的身份请求头，再写入经过认证的值。
- 后端配置可信代理范围，不允许绕过 oauth2-proxy 直连。
- Agent Worker 不接收浏览器身份 Header，只接收服务端签发的内部任务身份。

本地开发允许显式启用开发用户，但必须满足 `NODE_ENV != production` 和独立的开发配置。生产环境缺少认证请求头时必须返回 `401`，不能回退为默认用户。

#### 授权规则

认证只回答“用户是谁”，业务授权仍由 QianFu 服务端负责：

- 读取、修改、导出战役前验证 `gameInstanceId` 所有权或成员权限。
- 创建分享链接、撤销分享和下载私人档案只能由战役所有者执行。
- 多人战役根据 `campaign_members` 中的角色区分所有者、参与者和只读观察者。
- 分享页使用独立的高熵 `shareId`，不能把登录 Cookie 或用户 ID 当作分享凭证。
- 所有授权判断在服务端完成，前端隐藏按钮不能代替权限校验。

### 16.12 Agent 与模型故障降级

Agent 请求必须拥有明确状态，不能让一次模型调用直接决定是否扣除时间或修改世界：

```text
queued → running → succeeded
                  ├→ degraded
                  ├→ pending
                  └→ failed
```

请求处理规则：

- 超时只允许有限次数重试，重试使用同一个幂等键。
- 非法 JSON 允许一次结构化修复，仍失败则进入对应降级路径。
- 模型供应商故障、配额耗尽和网络错误必须区分记录。
- Agent 生成的语言可以失败，但规则引擎不能因此重复推进时间。
- 所有 Agent 调用保存 provider、model、promptVersion、耗时、Token 估算和结果状态。

三类降级：

| 场景 | 降级行为 | 时间处理 |
|:---|:---|:---|
| 普通对话 | 使用基于 NPC 关系、目标和知识的规则化回复，或提示稍后继续 | 只有成功生成回复并完成结算才扣除交谈时间 |
| 后台 NPC 行动 | 使用日程、目标优先级和风险规则推进 | 仍可推进计划，但不生成复杂叙事 |
| 关键剧情、招募和结算 | 写入 `pending`，等待恢复或管理员重试 | 不重复扣时间、不重复发放情报、不重复触发事件 |

规则化对话回复必须明确标注为有限回应，不应伪装成一次成功的深度交谈。关键行动恢复后要从保存的输入和状态版本继续，而不是重新生成一个可能不同的行动。

### 16.13 快照、事件日志与崩溃恢复

事件日志采用实例内单调递增的 `eventSeq`，快照保存最后已经应用的事件号：

```ts
interface WorldSnapshot {
  gameInstanceId: string;
  stateVersion: number;
  lastAppliedEventSeq: number;
  capturedAt: string;
  state: WorldState;
}

interface GameEvent {
  id: string;
  gameInstanceId: string;
  eventSeq: number;
  idempotencyKey: string;
  type: string;
  occurredAt: string;
  payload: unknown;
}
```

一次行动必须在同一事务中完成：写入行动事件、推进世界时间、写入状态版本和更新事件队列。恢复流程为：

```text
读取最新快照
    ↓
读取 lastAppliedEventSeq 之后的事件
    ↓
按 eventSeq 顺序重放
    ↓
验证状态版本和前置条件
    ↓
恢复未完成 Action 的 pending 状态
```

如果服务在行动中途崩溃：

- 已提交的事件只应用一次。
- 未提交的行动不扣时间、不改变状态。
- 已提交但 Agent 未完成的关键行动保持 `pending`，不能自动重复执行。
- 已进入 `finished` 的战役设置 `closedAt` 和最终报告版本，禁止新的业务写入。
- 内容版本和引擎版本随快照保存，旧战役恢复时继续使用原版本。

### 16.14 战报分享的隐私与生命周期

分享流程必须经过：

```text
生成脱敏预览 → 玩家主动确认 → 冻结报告版本 → 创建分享 token
```

默认规则：

- 公开分享页使用 `noindex`，不进入搜索引擎索引。
- `shareId` 使用高熵、不可枚举、与用户 ID 无关的随机 token。
- 分享链接只指向冻结的报告快照，不读取实时战役。
- 支持有效期、手动撤销和重新生成链接。
- 记录访问时间、报告版本和结果，不记录分享访问者的完整身份或其私有数据。
- 用户删除账号时，默认撤销其公开分享并删除或匿名化访问日志。
- 私人完整档案只能由战役所有者或明确授权的导出任务读取。
- 报告生成失败时保留战役结算状态，允许重新生成同一版本的报告。

### 16.15 潜伏剧本包与内容版本

QianFu 主要服务于潜伏类战役。通用引擎负责时间、对话、情报、招募、暴露、通信和结算；每个剧本只提供数据和受控配置。

```text
campaigns/
└── linjiang-1942/
    ├── campaign.json
    ├── locations.json
    ├── characters.json
    ├── missions.json
    ├── intel.json
    ├── events.json
    ├── endings.json
    ├── prompts/
    └── assets/
```

每个剧本必须有：

- `campaignId`、`campaignVersion` 和兼容的 `engineVersion`。
- JSON Schema 校验过的地点、人物、任务、情报和事件数据。
- 唯一 ID 和引用完整性检查，禁止引用不存在的 NPC、地点或情报。
- 明确的起始时间、入口任务、结束条件和启用模块。
- 发布状态：`draft`、`review`、`published`、`deprecated`。

剧本发布前执行静态校验和最小模拟。战役创建时固定 `campaignId + campaignVersion`；已开始的战役不受新内容版本影响。第一阶段禁止剧本包执行任意代码，事件只能使用引擎提供的受控条件和效果。

### 16.16 未来多人接口预留

短期不实现多人共享战役。当前 MVP 中，一个 `gameInstanceId` 只属于一个用户，所有行动按单玩家顺序推进。

数据库可以预留：

```ts
interface CampaignMember {
  gameInstanceId: string;
  userId: string;
  role: "owner" | "player" | "observer";
  status: "invited" | "active" | "left" | "removed";
  joinedAt: string;
}
```

未来多人再实现邀请、加入、退出、移除、断线恢复和私密行动权限。届时共享世界时间和 NPC 状态，但每个玩家的私有情报、私聊和秘密任务仍按 `userId` 隔离。预留表结构不代表当前开放多人 API。

### 16.17 可观测性与运营指标

服务上线后必须区分业务指标、Agent 指标和基础设施指标：

| 类别 | 指标 |
|:---|:---|
| 战役 | 创建数、活跃数、完成率、平均时长、结局分布、放弃率 |
| 玩法 | 每局行动数、对话轮数、招募成功率、情报验证率、暴露率 |
| Agent | 请求数、延迟、超时率、非法 JSON 率、降级率、Token 和成本 |
| 队列 | pending 数、事件堆积时间、重试次数、Worker 利用率 |
| 分享 | 报告生成成功率、分享创建数、访问数、撤销数、过期数 |
| 安全 | 未授权访问、身份 Header 异常、越权尝试、限流触发 |

日志必须包含 `requestId`、`gameInstanceId`、`userId`（可脱敏）、`agentRunId` 和 `eventSeq`，但不得记录完整隐藏 Prompt、密码本和未脱敏私有情报。应为 Agent 超时、事件堆积、跨实例访问和报告生成失败配置告警。

### 16.18 长篇章节故事模式

长篇故事是独立于难度的内容形态。它由多个可独立结算的章节战役组成，但人物命运、组织网络、资金和关键选择会延续到后续章节，最终共同指向一个预先定义的长期目标。建议首部长篇包含 6-10 章，每章覆盖 3-21 个游戏日，完整体验约 20-40 小时。

#### 故事结构与章节解锁

```text
长篇故事实例 StoryRun
├── 第一章：建立潜线与识别第一名同志
├── 第二章：由已招募同志接棒，建立交通站
├── 第三章：扩展电台与跨城联络
├── 分支章节：营救、撤离或重建受损网络
└── 终章：完成贯穿全篇的战略目标
```

每章必须在内容包中声明入口状态、核心目标、可选目标、截止条件和 `ChapterGate`。章节门槛由规则引擎判定，不能依靠主控 Agent 主观决定。例如第一章要求说服并保护“顾明远”，第二章才允许以顾明远为主角，从他的身份和人脉继续行动。

```ts
interface ChapterGate {
  requiredFacts: string[];
  requiredCharacters: Array<{
    characterId: string;
    allowedStates: Array<"recruited" | "active" | "extracted">;
  }>;
  minimumNetworkCapabilities: string[];
  minimumAvailableFunds?: number;
  alternativeGateIds?: string[];
}
```

必要要素必须可追溯、可预览：章节结算要明确显示“已满足”“尚未满足”和可用的补救路径。重要人物牺牲、失踪或招募失败可以关闭原路线，但不应在数十小时后才宣告整段存档无效；内容应预设营救、替代联络人、组织重建或不同结局等分支。真正不可逆的失败必须在玩家作出决定前给出符合角色认知的风险提示。

#### 跨章节继承与角色接棒

长篇故事使用一个 `storyRunId` 关联多个章节 `gameInstanceId`。单章仍保留独立事件日志、快照、结算和战报，跨章只通过经过校验的 `StoryCarryover` 传递允许继承的状态：

- 存活、失踪、被捕、撤离和已招募人物及其关系变化。
- 已建立的交通站、安全屋、电台、联络线和组织能力。
- 资金余额、物资储备、长期承诺和固定维护成本。
- 已确认的关键事实、组织声望、敌方长期关注与历史债务。
- 会影响后续章节的公开选择和不可逆后果。

章节可以更换玩家角色。上一章招募的同志可以成为下一章主角，原主角则转为上级、联络人、失踪对象或可自主行动的同志 Agent。新主角只能继承组织明确交接给他的情报，不能自动获得前任的全部私有记忆。这样既保留连续性，也继续遵守 Agent 知识隔离。

#### 资金与地下网络经营

资金是长篇故事的战略资源，不加入现有短期战役的逐餐记账。系统维护组织总账，并在每日或每周结算固定开支：

| 收入来源 | 特点与风险 |
|:---|:---|
| 组织拨款 | 相对可靠，但受交通线和上级状况影响 |
| 合法职业或商号收益 | 可持续，同时需要维持公开经营和合理账目 |
| 同情者捐助 | 依赖关系，频繁索取会增加对方压力和暴露风险 |
| 特别行动所得 | 收益高但风险大，不能成为无代价刷钱渠道 |

| 支出项目 | 产生的能力 |
|:---|:---|
| 安全屋租金与伪装经营 | 提供隐蔽会面、住宿和紧急藏匿 |
| 地下交通站维护 | 提高人员、情报和物资跨区传递能力 |
| 同志生活与安置费 | 降低成员压力，维持长期工作能力 |
| 电台、密码本和维修 | 维持通信能力与信息安全 |
| 证件、交通、医疗和营救 | 支撑具体行动或处理突发损失 |
| 紧急撤离准备金 | 在网络暴露时保留人员和火种 |

资金不足不应只显示负数，而要产生可选择的后果：关闭或降级据点、拖欠补助、暂停通信、请求高风险拨款，或让某条交通线暂时休眠。资金充足也不能直接购买 NPC 忠诚或消除暴露；每笔异常收入和大额支出都可能形成敌方可调查的账目痕迹。

地下网络节点至少包含 `upkeep`、`capacity`、`concealment`、`exposure` 和 `status`。玩家需要在扩张速度、维持成本和安全性之间取舍。章节门槛应优先检查“网络是否具备某种能力”，而不是只检查攒够多少钱，避免把谍战游戏变成单纯资源刷取。

#### 长期目标与结算

每部长篇故事必须在内容清单中固定一个贯穿全篇的最终目标，例如建立覆盖三座城市的可靠情报网，并在终章保证关键战略情报及时送达。每章的胜负会改变终章条件，而不是简单累计分数。

长篇结算除单章评分外，还应评价：战略目标完成度、组织网络保留程度、关键同志命运、情报贡献、资金纪律、平民与组织代价，以及玩家留下的长期影响。最终可生成一份包含章节年表、历任主角、人物去向、网络兴衰和关键抉择的“长篇档案”，供玩家下载和分享。

#### 内容版本与 Agent 上下文

长篇内容包增加 `story.json`，声明章节顺序、分支、门槛、继承白名单和最终结局。创建 `StoryRun` 时固定故事主版本；每个章节开始时再固定其具体内容版本。若后续修订尚未开始的章节，必须通过显式兼容迁移，不能静默改变已获得的解锁条件。

主控 Agent 不直接装载数十小时的完整记录。进入新章时由规则引擎生成结构化历史摘要，并按当前角色权限提供人物关系、已知事实、组织状态和未偿债务；需要追溯时再按事件 ID 检索原始记录。NPC Agent 仍只获得该人物亲历或被告知的跨章记忆。

#### 当前预留接口

这部分在 `Phase 5` 前不实现业务逻辑、不创建资金账本，也不在当前 API 中注册空路由。当前阶段只保证战役模型和内容包不会阻断未来扩展：

```ts
interface GameInstanceLink {
  experienceMode: "standalone" | "chronicle";
  storyRunId?: string;
  chapterId?: string;
  chapterSequence?: number;
}

interface StoryRunSummary {
  storyRunId: string;
  storyId: string;
  storyVersion: string;
  difficultyPreset: "guided" | "undercover" | "ironCurtain";
  status: "active" | "paused" | "finished" | "failed" | "abandoned";
  currentChapterId: string;
  completedChapterIds: string[];
  availableChapterIds: string[];
  funds: { available: number; reserved: number; currency: string };
  updatedAt: string;
}

interface StoryCarryover {
  sourceGameInstanceId: string;
  targetChapterId: string;
  characterStates: Record<string, "active" | "missing" | "captured" | "dead" | "extracted">;
  relationshipRefs: string[];
  inheritedFactIds: string[];
  networkNodeIds: string[];
  networkCapabilities: string[];
  availableFunds: number;
  reservedFunds: number;
  consequenceIds: string[];
  lastEventSeq: number;
}
```

未来服务接口统一放在 `/api/v1/story-runs` 下，避免把跨章聚合状态塞进现有单场 `/games` 接口：

| 方法与路径 | 用途 |
|:---|:---|
| `POST /api/v1/story-runs` | 根据已发布的 `storyId`、版本和难度创建长篇实例 |
| `GET /api/v1/story-runs/:id` | 获取玩家可见的长篇进度、当前章和资源摘要 |
| `GET /api/v1/story-runs/:id/chapters` | 获取章节状态、解锁门槛和可用补救路线 |
| `POST /api/v1/story-runs/:id/chapters/:chapterId/start` | 校验门槛后创建该章的独立 `gameInstanceId`，要求幂等键 |
| `POST /api/v1/story-runs/:id/chapters/:chapterId/settle` | 冻结章节结算并原子生成 `StoryCarryover`，仅供内部结算流程调用 |
| `GET /api/v1/story-runs/:id/ledger` | 分页读取玩家可见的资金收支与维护预测 |
| `GET /api/v1/story-runs/:id/network` | 读取跨章组织节点、能力、维护成本和公开风险 |
| `GET /api/v1/story-runs/:id/archive` | 获取长篇年表和最终档案；结束前只返回已完成章节 |

所有接口沿用现有 OAuth2 用户身份和所有权校验。章节启动、结算和资金变动必须写入带单调事件序号的事件日志；客户端不能直接提交余额、人物状态或解锁结果，只能提交受控行动或启动请求。当前独立战役默认返回 `experienceMode: "standalone"`，可选字段缺失时必须保持向后兼容。

### 16.19 字段级情报来源与交叉核验

情报可信度不能只表现为一个百分比。每个已知字段都保存可供玩家复盘的证据记录，形成“情报条目 -> 字段 -> 来源证据”的链路。

每条证据至少包含：证据 ID、字段、直接来源、来源类型、上游来源、取得时间、玩家可见摘要和核验判断。来源类型包括人物证言、文件记录、现场观察和同志回报；核验判断包括：

- `unverified`：目前只有一个来源，尚未核验。
- `corroborates`：新的独立上游来源印证已有记录。
- `contradicts`：新的独立来源与已有记录冲突，需要继续判断。
- `dependent`：看似来自不同人物，但追溯到同一文件、传闻或上游联系人，不能重复计为独立核验。

规则引擎负责判断来源是否独立以及可信度变化，NPC Agent 只负责以角色口吻表达自己知道的内容，不能直接修改证据状态。`sourceOrigins` 属于剧本定义的后台元数据，玩家界面只显示“同源转述”及可理解的摘要，不泄露内部来源 ID、情报真值或人物隐藏可靠性。

“核验情报”对话必须选择一份当前已知、且该 NPC 有权限接触的具体情报。对话会话保存 `targetIntelId`，后续每轮沿用同一目标；服务端再次校验 NPC 与情报的来源关系，不能依靠前端限制。已招募同志执行收集或核验任务时，也必须写入同一种证据记录，不能直接无来源地提高可信度。

前端提供独立的“情报档案”：按情报和字段展示证据时间线、来源、独立印证、矛盾与同源关系，并提示下一步需要寻找独立来源或消解冲突。电报编制器对选中字段检查证据链；存在矛盾、缺少独立印证或只有同源转述时明确警告，但允许玩家承担风险继续发送。

存档兼容规则：旧战役缺少 `evidence` 时初始化为空数组；公开玩家状态可以包含玩家已取得的证据，但必须过滤内部真值和隐藏人物状态；结算报告只保存证据统计摘要，公开分享不暴露后台来源映射。已开始战役继续固定其剧本版本，新增的来源元数据只影响兼容该内容版本的规则执行。

验收测试至少覆盖：独立来源可以印证、共同上游只能判为同源、部分真相可以产生矛盾、核验对话绑定具体情报、同志回报进入证据链、旧存档迁移、公开状态不泄露隐藏字段，以及电报风险提示与选中字段一致。

### 16.20 行动日志与任务目标面板

战役主界面必须同时提供“当前目标摘要”和“完整行动时间线”。目标数据由服务端根据固定剧本目标和公开世界状态计算，前端不能自行判断结算：

- 目标显示标题、截止时间、剩余游戏分钟和状态（进行中、待传递、已完成、已逾期）。
- 每个目标列出所需情报、字段完成情况、当前可信度、最低可信度要求、已送达字段和缺失字段。
- 目标只有在必需字段齐全、可信度达到要求、使用允许渠道送达并产生组织回执后才显示为已完成。
- 状态为“待传递”时提示玩家可以安排电报或交通员；逾期只表示当前目标失败风险，不由前端直接结束战役。
- 所有计算使用战役 `currentTime`，不能使用浏览器现实时间代替游戏时间。

行动日志读取该 `gameInstanceId` 的公开事件日志，按事件序号和游戏发生时间排序。日志至少覆盖移动、等待、对话、人物发现、情报记录与传递、同志任务、收发电报和敌方调查行动；服务端过滤调查内部证据、NPC 私密意图和系统 Prompt 后才返回前端。界面默认显示最近事件，并提供按对话、情报、行动、同志和敌方动静筛选的完整时间线；日志只读，不能作为修改状态的接口。

目标和日志必须与自动保存、导出档案和结算报告使用同一事件源。刷新页面或切换设备后，玩家仍能看到完整历史；重复请求不会重复显示事件。验收标准是玩家能够不依赖开发者说明回答“当前缺什么、何时截止、是否可以传递、为何还不能结算”，并能从时间线复盘导致风险变化的关键行动。

### 16.21 公开身份工作与考勤压力

MVP 玩家固定使用“机要处档案员”公开身份。公开身份状态 `cover` 独立于秘密关系和网络状态保存，并至少包含：`workStatus`（待岗、正常工作、请假、异常缺勤）、公开信誉、上级怀疑、连续缺勤天数、请假次数、已完成工作日期、最近工作时间和同事/上级观察记录。旧战役缺少该状态时，恢复为默认公开信誉，不能导致读档失败。

### 16.22 开局掩护身份与线索式发现

开始独立战役前，玩家选择无姓名、无隐藏阵营信息的公开履历，而非扮演任何现有 NPC。MVP 提供机要处档案员、南北货行商、自由撰稿人三种履历；每种履历定义起点、合理活动地点与时段、公开工作选项、每日可核验记录和唯一初始公开联系人。档案员维持机关考勤；行商以货账、拜访客户和存货周转证明行踪；撰稿人以交稿、校对和采风证明行踪。公开身份只能影响活动约束、初始关系与风险，不能暴露 NPC 是否可招募或其隐藏立场。

地点与人物必须按线索发现。新战役只显示起始地点，且只有履历对应的一名公开联系人可正式对话；到达地点、同处一室、观察陌生人都不能自动获得姓名或开启对话。已认识 NPC 在有效情报对话、任务回报或交通员侦察中可提供受控的地点路线与人物引介，规则引擎记录 `location.discovered` 和 `character.introduced` 事件及其来源。客户端只能展示已发现地点和已获引介人物；未知对象保持为“？？？”，服务端拒绝对未引介人物发起对话、甄别或招募。旧战役保留原有已发现列表，不因升级锁回已经取得的知识。

首层引介优先由公开身份和世界事件产生，而不是要求玩家第一次见面就索取敏感情报。每个剧本可声明 `publicLeads`：它以公开工作类型或一次已成立的对话发现为触发条件，提供可解释的办事理由、解锁地点和可正式接触的人物。档案员可因核对维修单认识电讯科技术员，行商可因货账差异前往码头，撰稿人可因校样来源联系饭店或商会；这些线索不得包含人物隐藏立场、可靠度、是否可招募或任何秘密任务信息。引擎将已执行的 `leadId` 保存到 `resolvedLeadIds`，并写入 `lead.resolved`、`location.discovered`、`character.introduced` 事件，防止读档恢复和重复请求重复引介。内容校验必须检查引介 ID 唯一、触发参数完整及地点/人物引用有效。

关键情报不能因一次长谈被批量授予。常规索取至少要求基础熟悉度和私下信任；剧本可按情报来源额外配置 `sourceRequirements`，分别规定某 NPC 对该情报的熟悉度和信任门槛。对话轮次只按比例累积关系，一次对话会话最多形成一个情报字段或一次核验，因此同一人物的下一条细节需要新的会面、时间成本和风险窗口。关键目标应把字段分配给至少两名独立来源，并用公开引介把玩家从首位联系人带到后续人物和地点；不得让玩家只靠同一人物连续索取就完成核心任务。战报的关键时间线必须记录公开工作、公开引介、具体情报名称和字段标签，而不能只写笼统的“获得线索”。

### 16.23 夜间休息与精力恢复

精力是行动节奏约束，不应因两分钟对话轮次被机械扣空。移动、观察、公开工作、甄别和长时秘密行动按时长与强度消耗精力；等待和对话轮次不单独扣除。玩家可在 20:00 后至凌晨启动 `rest` 行动，选择次日 06:00、07:00 或 08:00 起床，且必须满足至少六小时睡眠。服务端计算真实跨夜时长，休息期间照常推进十分钟世界时钟、NPC 日程、组织任务、回执、敌方事件和公开身份考勤，但不扣精力，并按睡眠时长恢复精力（上限 100）。凌晨继续行动会增加体力成本；休息与恢复数值必须写入 `player.rested` 事件、行动日志和最终战报。客户端不得提交自定义休息时长或恢复量。

甄别行动不再是无上下文的按钮。玩家进入计划编写界面，填写行动目标、执行步骤、风险控制和撤退条件；服务端限制各字段长度、步骤数量和可产生的状态变化。界面提供按甄别类型生成的“稳妥计划”，玩家可以直接采用后再提交。计划作为 `RecruitmentEvidence.plan` 与事件日志的一部分保存，支持战报复盘。

计划提交后进入独立的 `ScreeningActionAgent`。该 Agent 只能获得候选人公开身份、人格投影、当前场景和玩家计划，只返回候选人在执行中的可观察行为描述，不得返回隐藏阵营、可靠性真值、后台数值或直接修改世界状态。主控 Agent/规则引擎负责校验计划、计算消耗时间、推进十分钟时间线、根据固定剧本可靠性与计划质量判定结果，并写入证据事件。模型超时、非法 JSON 或不可用时，使用规则化观察文本继续执行，不重复扣除时间。

公开工作时段为游戏时间 08:00-17:00，且只能在机要楼档案科进行。玩家每天只能选择一项公开工作：整理档案（60 分钟）、完成值班（120 分钟）或提交例行报告（30 分钟）。工作会产生可被同事核对的公开记录，提高信誉、降低上级怀疑，并略微缓解个人怀疑；它不是免费等待，仍消耗游戏时间和精力。请假需要在工作时段到档案科办理，消耗 10 分钟，可选择家庭事务、身体不适或公务外出，登记至当日班次结束；请假不会计为缺勤，但重复请假会轻微增加上级怀疑。

每次世界时钟跨过当天 17:00 时，规则引擎结算该日考勤：没有工作记录且没有有效请假的玩家获得异常缺勤，降低信誉、提高上级怀疑与个人怀疑，并作为敌方可利用的公开异常写入调查证据。连续两天缺勤或上级怀疑达到阈值时，触发上级核查事件和额外个人压力。工作完成后清除连续缺勤，但已经发生的观察记录保留在档案中。NPC Agent 不决定考勤或惩罚，主控规则只将公开事件提供给叙事层。

最终评分的“掩护”分数由个人怀疑、公开信誉和上级怀疑共同计算；公开身份状态也应显示在私人结算档案中。前端公开身份面板必须展示当前状态、信誉、上级怀疑、缺勤/请假统计、最近观察，并只在地点和时间符合条件时开放工作与请假按钮。行动日志包含完成工作、请假、异常缺勤和上级核查，方便玩家复盘。验收测试覆盖：按时工作不记缺勤、有效请假不记缺勤、连续缺勤触发核查、旧存档迁移、公开身份影响评分，以及工作和请假参数不能由客户端伪造。

## 十七、MVP 范围

第一版目标不是完整战役，而是一段可重复体验 45-60 分钟的纵向切片。

### 17.1 内容范围

- 1 个街区，6 个可访问地点。
- 3 个游戏日。
- 8 名重要 NPC，其中 3 人可招募。
- 1 名潜在双面人员，身份在新游戏时可按种子变化。
- 10-12 条情报碎片，组成 2 项核心情报。
- 电报和交通员两种传递方式。
- 1 个公开身份工作系统。
- 1 个敌方调查 Agent。
- 3 种结局：成功传递、情报错误、网络暴露。
- 战役自动保存、结算冻结和 HTML/JSON 战报导出。
- 分享链接的脱敏预览、有效期和撤销能力。
- Agent 故障时的对话、后台行动和关键剧情降级路径。
- 任务结局、部分成功和评分报告。

### 17.2 MVP 核心任务

> 三天内确认一批无线电设备的运输时间与地点，并把可靠情报送出城。玩家可以亲自调查，也可以尝试招募内部人员协助。

这个任务足以验证时间、关系、甄别、情报、传递和敌方反制的完整循环。

### 17.3 MVP 暂不实现

- 大型开放城市。
- 多玩家模式。
- 战斗和枪械系统。
- 无限数量的自由 NPC。
- 自动生成完整战役。
- 复杂经济与生存系统。
- 长篇章节故事、跨章角色接棒和资金经营；MVP 只预留 `experienceMode` 与 `storyRunId` 扩展位。
- 语音对话。

## 十八、开发阶段

### Phase 0：纸面模拟

- 确定 8 名 NPC、日程和隐藏身份。
- 用表格手工运行三天时间线。
- 验证玩家是否能通过证据判断候选人，而不是依赖猜测。
- 确定行动耗时和关键任务窗口。

验收标准：不用大模型也能完整跑通一局。

### Phase 1：规则原型

- 世界时钟和事件队列。
- `gameInstanceId`、用户所有权和实例级状态隔离。
- 复用 oauth2-proxy + Casdoor OIDC，并实现同步用户 upsert。
- 地点、移动、日程和相遇。
- 玩家行动与时间消耗。
- NPC 结构化状态和知识隔离。
- 固定文本的情报获取与传递。

验收标准：同一随机种子可以稳定重放。

### Phase 2：Agent 接入

- 共享 Agent Worker 池和实例级上下文装载。
- 主控 Agent 生成场景叙事。
- NPC Agent 进行对话和短期计划。
- 招募成员转为自主 Agent。
- 敌方调查 Agent 基于证据行动。
- 所有输出使用 JSON Schema 验证。
- Agent 超时、非法 JSON、服务不可用时使用降级或 `pending` 状态。

验收标准：Agent 无权制造物品、瞬移或读取不属于自己的秘密。

### Phase 3：完整 MVP

- 情报板、人物档案和组织网络 UI。
- 电报编码与发报风险。
- 招募、测试、权限和同志委派。
- 三日任务和三个结局。
- 存档、读档与行动日志。
- 结算报告、私人档案下载和脱敏分享链接。
- 内容包校验、剧本版本固定和报告生命周期管理。

验收标准：新玩家能独立完成一局，并能解释主要成功或失败原因。

### Phase 4：内容扩展

- 14-21 天完整战役。
- 更多部门、街区和组织派系。
- 动态身份组合和多周目变化。
- 更多通信方式与组织管理策略。
- 人物长期关系和个人支线。

### Phase 5：长篇故事

- 将现有低难度“故事模式”完成迁移并统一命名为“引导模式”。
- 建立 `StoryRun`、章节门槛、分支和跨章继承模型。
- 实现资金总账、据点维护、交通站和组织能力系统。
- 支持角色接棒、跨章知识隔离和结构化历史摘要。
- 制作 6-10 章的首部长篇内容，并定义贯穿全篇的最终目标。
- 生成章节年表和可下载、可分享的长篇档案。

验收标准：玩家可以从第一章连续推进至终章；人物、资金、组织能力和重大后果能够稳定跨章继承，失败路线具有明确且可测试的补救或分支结果。

## 十九、测试与评估

### 19.1 规则测试

- 时间只能向前推进。
- 人物同一时间不能出现在两个地点。
- 玩家不能使用未获得的情报或物品。
- NPC 不能知道未亲历、未获告知的事实。
- 情报过期、传递和截获结果可稳定复现。
- 被隔离小组泄密时，敌方只能获得该成员知道的部分。
- 两个游戏实例使用同一 NPC 原型时，位置、记忆、招募和风险状态互不影响。
- 同一实例的并发请求只能成功推进一次时间线。
- 异步任务重试不会造成重复发报、重复奖励或重复事件。
- 结算后的战报内容保持不变，不受后续战役操作影响。
- 公开战报不会泄露隐藏阵营、私人情报、其他玩家数据或内部 Prompt。
- 分享链接过期或撤销后不能继续读取报告。
- 私人完整档案只能由战役所有者下载。
- 模型服务超时或不可用时，普通对话、后台行动和关键剧情分别走预定降级路径。
- 失败重试不会导致重复扣除时间或重复修改 NPC 关系。
- 内容包引用不存在的 ID、错误版本或非法事件效果时无法发布。
- 战役固定的剧本版本不受后续内容发布影响。
- 结局状态、评分分项和报告内容可以从同一事件日志重算得到。
- 伪造 `x-forwarded-user` 的公网请求不能绕过 oauth2-proxy 获得身份。
- 首次登录并立即创建战役时，不会因异步注册产生用户外键竞态。
- 用户修改展示名称或邮箱后，仍通过稳定 OIDC `sub` 关联原有战役。
- 生产环境缺少认证身份时返回 `401`，不能回退到开发用户。

### 19.2 Agent 测试

- 对话角色一致性。
- 隐藏信息不泄露。
- 面对提示词注入时不输出服务端状态。
- NPC 计划符合地点、时间和资源约束。
- 同一 NPC 在压力变化前后行为具有连续因果。
- 主控 Agent 不为制造戏剧效果强行改变事实。
- Agent Worker 处理完实例 A 后，下一次处理实例 B 时不保留 A 的上下文。
- 玩家输入中的提示词注入不会改变系统规则、权限或隐藏信息。

### 19.3 玩法指标

- 玩家每 10-20 分钟获得一次有意义的新信息或局势变化。
- 一个关键决定至少存在两种合理方案。
- 招募对象不能只靠一次对话确定身份。
- 玩家失败后能指出一个可改进的决策。
- 不调用大模型时，规则原型仍然可以完成一局。
- 单个普通行动不应触发超过 1-3 次模型请求。

## 二十、主要风险与处理

| 风险 | 后果 | 处理方式 |
|:---|:---|:---|
| 主控 Agent 权力过大 | 剧情随意、状态矛盾 | 状态机拥有最终权威，Agent 只提出事件 |
| NPC 数量过多 | 延迟与成本失控 | 分级激活，后台人物使用日程模拟 |
| 可靠性完全随机 | 玩家无法推理 | 身份随机但证据链必须一致且可验证 |
| 可靠性完全可见 | 招募失去紧张感 | 展示证据与估计，不展示真值 |
| LLM 决定全部成败 | 无法平衡和复盘 | 规则决定结果，LLM负责行为表达 |
| 自由输入范围无限 | 玩家轻易绕过玩法 | 自由文本解析为受控行动和意图 |
| 每十分钟都无事件 | 节奏拖沓 | 支持连续行动和快速推进到下一事件 |
| 每十分钟都有危机 | 玩家疲劳 | 区分日常压力、线索和真正危机 |
| 多用户状态串线 | 泄露隐藏信息并破坏存档 | 所有状态按 `gameInstanceId` 分区并验证所有权 |
| 单个玩家占满 Agent | 其他玩家延迟上升 | 用户配额、任务队列、公平调度和超时控制 |
| 并发推进同一时间线 | 重复事件和状态冲突 | 实例锁、状态版本和幂等键 |
| 伪造代理身份 Header | 越权读取或修改他人战役 | 只信任 oauth2-proxy，清理外部 Header，限制服务直连 |
| 首次登录异步注册竞态 | 战役创建失败或产生孤立数据 | 业务写入前同步 upsert 用户 |
| 用户名变化导致身份漂移 | 用户失去原有战役关联 | 使用 OIDC `sub` 作为稳定外部身份 |
| Agent 服务不可用 | 行动卡死或重复扣除时间 | 明确降级状态、pending 状态和幂等重试 |
| 剧本内容引用错误 | 运行时找不到人物或事件 | 发布前 JSON Schema、引用和最小模拟校验 |
| 报告版本不一致 | 分享结果与战役结算不符 | 结算冻结报告版本，按版本重生成 |

## 二十二、最终建议

这个项目最重要的技术与玩法决定是：**不要让主控 Agent 直接讲完整个故事，也不要让每个 NPC 无限自由行动。**

最佳结构是：

1. 确定性时间与规则引擎保存真实世界。
2. 主控 Agent 负责节奏、调度和玩家可见叙事。
3. NPC Agent 只根据自己的知识、目标和压力做选择。
4. 招募成员成为自主 Agent，但受到能力、纪律、信息权限和时间约束。
5. 玩家通过证据持续判断可靠性，系统永远不直接显示标准答案。

第一步应先制作“三天确认运输计划”的纸面原型。只要这个小任务在没有华丽对话时依然紧张、有推理空间，多 Agent 接入后才能真正增强游戏，而不是掩盖规则不足。
## 玩家存档槽位（MVP）

每个战役固定提供两个玩家存档槽位（`1`、`2`）。存档是服务端权威快照，包含完整 `WorldState`、战役/引擎版本、状态版本、当前游戏时间和最后事件序号；不依赖浏览器本地存储，也不会影响其他用户或其他战役。

- 玩家可在战役处于 `active` 或 `paused` 时覆盖任一槽位；覆盖前端必须二次确认。
- 加载槽位前必须明确提示“保存点之后的行动将被丢弃”，并二次确认。只允许加载尚未结算的战役；已结算战役及其报告、分享页保持只读。
- 加载在数据库事务中锁定战役，校验所有权及版本兼容性，恢复完整状态，并删除保存点之后的事件和幂等动作，使后续行动从保存点继续且事件序号保持单调递增。
- 槽位只返回摘要（标签、保存时间、游戏时间、状态版本、事件序号），不会在列表接口泄露完整状态；保存记录按战役级权限隔离。
- 旧的 `game_snapshots` 继续用于崩溃恢复，不展示为玩家槽位。

验收：两个槽位可独立保存、覆盖、加载；加载后地点、人物记忆、情报、时间线和风险值全部回到保存点；保存点之后的事件不可见且不会再次触发；并发保存/加载不会产生跨战役数据。
